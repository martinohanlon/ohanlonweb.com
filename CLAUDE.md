# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Martin O'Hanlon's personal CV/portfolio site: a static Jekyll site on GitHub Pages, migrated
from Google Sites. Two pages (`index.md` home, `about.md` CV), monospace/terminal-prompt design
theme, light/dark toggle. See `README.md` for the fuller structure/purpose writeup.

## Commands

```
bundle install                              # install gems (Ruby 3.x + Bundler required)
bundle exec jekyll build                    # build to _site/, fails loudly on Liquid/config errors
bundle exec jekyll serve                    # preview at http://127.0.0.1:4000
bundle exec ruby bin/update-blog-posts.rb   # regenerate _data/blog_posts.yml from the RSS feed
```

There is no test suite or linter — "testing" a change means building/serving locally and
checking both pages (and both themes) in a browser.

### Deploying

Nothing is committed directly to `main`. Work happens on `development`; publishing is a
fast-forward merge, which is what triggers the build/deploy workflow:

```
git checkout main && git merge development --ff-only && git push origin main
git checkout development
```

`.github/workflows/pages.yml` then runs `bin/update-blog-posts.rb`, builds, and deploys —
on that push, weekly on a schedule, and on manual dispatch. Watch it with `gh run list` /
`gh run watch <run-id>`.

## Architecture

**Pages mix Markdown and raw HTML deliberately.** `index.md`/`about.md` carry Jekyll front
matter and are `.md` so kramdown can render real prose (headings, the `.muted` intro
paragraph, the `.profile-list`/`.achievements-list` bullet lists) — but most of each page is
plain HTML section wrappers with Liquid loops over `_data/*.yml`, rendered through
`_includes/{card,list-row,testimonial,section-header}.html`. A block only needs
`markdown="1"` on its wrapper tag where actual Markdown syntax appears inside it; blocks that
are pure Liquid+HTML (card grids, list columns) are left as plain HTML and kramdown passes
them through untouched. When adding a new prose section, follow this pattern rather than
converting everything to Markdown or everything to HTML.

**Content vs. template split**: routine content changes (new blog post, testimonial, course,
article) go in `_data/*.yml`, not in the page files or includes — see the table in
`README.md`. `_data/blog_posts.yml` is regenerated by `bin/update-blog-posts.rb` and
overwritten on every build/deploy; don't hand-edit it, edits won't survive.

**kramdown typography is deliberately neutered** (`_config.yml`): `smart_quotes` and
`typographic_symbols` are pinned to pass characters through literally. Without this, kramdown
turns `--` into an en-dash and straight quotes into curly ones inside Markdown-rendered
text — breaking things like the literal `$ contact --martin` prompt-line text, and making
quote style inconsistent with the plain-HTML parts of the same page. Don't remove this
config to "fix" apostrophes; it's intentional.

**`baseurl` is hand-pinned in the CI build, not left to Jekyll to infer**, because of two
separate landmines discovered building this:
1. `github-pages` gem's `jekyll-github-metadata` plugin auto-computes a bogus baseurl
   (`/pages/<owner>/<repo>`) unless overridden — hence `PAGES_REPO_NWO`/`GITHUB_TOKEN` env
   vars are set for the metadata plugin, and `--baseurl` is passed explicitly regardless.
2. The site is currently served at `github.io/ohanlonweb.com/` (no custom domain configured
   in Pages settings yet, even though the `CNAME` file exists in the repo — Actions-based
   Pages deploys don't auto-read a `CNAME` file from the artifact the way the legacy
   branch-based builder did). So `baseurl` is `/ohanlonweb.com`, **not** empty, until DNS is
   pointed at Pages and the custom domain is set via the Pages API/settings — at which point
   it must flip to `""` (see the `TODO` comment at the build step in `pages.yml`). Verify any
   baseurl change by fetching the deployed page and checking what its own `<link>`/`<script>`
   hrefs resolve to, not just that some manually-constructed URL happens to 200.
3. The `github-pages` environment's deployment branch policy only allows `development` (the
   default branch) by default — `main` had to be added explicitly
   (`deployment-branch-policies` API) since the deploy workflow runs on pushes to `main`.

**Local testing on Windows/Git Bash**: MSYS path-conversion mangles any bash argument that
looks like a leading-slash path (e.g. `--baseurl "/ohanlonweb.com"` becomes a Windows path).
Use the `//ohanlonweb.com` double-slash escape when testing that flag manually in this shell;
it's not an issue in the actual (Linux) CI runner.

**Repo is public** (needed for GitHub Pages on GitHub Free, and for unlimited Actions
minutes) — check before adding anything that shouldn't be public.
